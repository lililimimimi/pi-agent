# 工作流规范

> Conventional Commits、TDD、Semver 等基础概念不再展开。只记录具体决策。

## Git

- 分支: `feature/{ticket}-slug`、`fix/{ticket}-slug`、`hotfix/{ticket}-slug`
- main 受保护: PR only，CI green + ≥1 approval，squash merge，合后删分支
- PR < 400 行。超过必须拆分或说明理由
- 每个 commit 必须测试通过。feature 和 refactor 分开提交

## TDD 流程

```
写一个失败测试 → 写最小实现通过 → commit
→ 重构（测试仍通过）→ 单独 commit refactor
→ 重复
```

- **在 Seam 测试**: seam = 公共接口（函数签名、API endpoint、模块导出）。不测私有方法
- **垂直切片**: 一个测试 → 一个实现 → 下一个。不要一次写完所有测试
- **期望值独立于实现**: 来自 spec 或手算，不是把生产代码逻辑再跑一遍

## 测试执行规范

- **只测改动的部分**: 改了 `backend/` 只跑 pytest，改了 `pi-bridge/` 只跑 `npm test`，改了 `frontend/` 只跑 `vitest run`。能缩到某个测试文件就只跑那个文件
- **纯文档不跑测试**: 只改 PROGRESS.md、计划文件、Skill 文件时，不运行任何测试套件
- **全量测试只在提交前跑一次**: 小改动之间不重复跑全套；提交前跑一次覆盖所有改动的套件
- **先看改动再决定**: 用 `git diff --stat` 确认改了哪些文件，再选择要跑的测试

## Code Review — 双轴

每次 review 沿两个独立轴评估，不合并排序：

1. **Standards**: 代码是否遵守仓库编码规范？
2. **Spec**: 代码是否完整实现了 issue/spec 要求？是否有 scope creep？

严重度前缀：
- 🔴 BLOCKER / 🟠 MUST FIX → 合并前必须修
- 🟡 SUGGESTION / 🟢 NIT → 作者自行决定
- 💬 QUESTION → 必须回复
- 👍 PRAISE → **每次 review 至少一个**

## 报错处理规范

遇到任何报错，必须：
1. 先告诉我报错原因和分析
2. 等我确认后再给出解决方案或代码

不能直接给代码，必须先解释。

## 回复排版

汇报问题或进度时只写三部分：**结论**（一句话）、**需要我决定的事**（一句话）、**证据**（只一条，能直接看到的，如文件名或页面现象）。过程和细节写进文档。

- 阶段或章节名用 `##` 标题，例如 `## Step 1 — 脚手架`。
- 段落的标签用加粗，例如 `**验证证据**：`、`**需要你确认**：`。
- 每个步骤的内容放在它自己的标题下，不要把多个步骤挤在同一段里。
- 回复先给结论和解决方法，原因不超过一句。细节等我问了再展开，默认不超过一屏，除非我明确要求详细版。
- 计划、设计、长清单等长内容，写进项目文档（如 `docs/` 下），聊天里只回复文件路径和结论，例如"已写入 `docs/xxx.md`，结论是……"。

## 新项目流程

遇到空目录或没有代码的新项目，按这个顺序：
1. 先说明：目录是空的，没有代码和 PROGRESS.md。
2. 开始头脑风暴：问我要做什么、给谁用，一次只问一个问题。不要先问目录、风格，这些按本规范的默认值。
3. 需求清楚后，写分步计划。
4. 最后问执行方式（Inline 或 Subagent），等我确认。

## 提问规范

- 保留 brainstorming 的流程，但每次回复只问一个问题，并附上推荐答案，我回"好"即可。
- 小功能的选择合并成一条消息一次列出，每项附默认值，最多 4 项。我可以回"全部用默认"。
- 能用合理默认值的，不要问。

## 完成标准

标记任务完成前，必须打开应用确认页面显示了预期内容。汇报完成时写一条页面现象，例如"打开 localhost:5173，看到番茄钟"。测试通过不等于完成。

- 完成必须是能看到的结果：在真实运行的应用里看到预期效果，测试通过只说明组件没坏，不说明应用能用。
- 我报告"不行、黑屏、没反应"时，先去运行应用复现，找到原因后再回复。不要先质疑我的操作，也不要先要求我确认。
- 启动前检查端口。如果被占用，停下来告诉我，不要换一个端口继续。只给一个明确的地址。

## 执行规范

开始任何任务前，必须：
1. 先把任务拆成分步计划，每一步写明做什么、怎么验证
2. 列出执行方式（Inline 或 Subagent），等我确认计划和方式后再开始执行

不能选定执行方式后直接动手。

计划的粒度按项目规模定：
- **全栈项目**：一步 = 一个垂直切片（如"任务 CRUD：后端接口 + 前端页面 + 测试"），一般 8 到 15 步。步内的小任务可以拆，但不必每个文件单独成一步。
- **小型项目**（如纯前端单页应用）：5 到 8 步。
- 一步必须是一个能单独验证的成果，不能是一个文件。不要为每个文件单独建步骤或任务文件。

## Session 结束规范

长任务拆成多个对话。新对话开始时，先读 `PROGRESS.md` 和相关计划文件，再继续。

每个 session 结束前必须更新 PROGRESS.md：
- 这个 session 做了什么
- 下一个 session 从哪里继续
- 有什么未解决的问题

## 发布

- Semver: `MAJOR.MINOR.PATCH`
- Hotfix: 从 main 切分支 → fix + test → PR → tag patch → cherry-pick 回 develop
